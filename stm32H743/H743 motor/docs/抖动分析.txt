你这个实测结果非常关键——它把问题从“硬件毛刺”转移到了“**高速下的算法量化噪声**”，这才是根因。

**4000 RPM 以下稳，4000 RPM 以上抖**，且电机物理上不可能高频震荡，说明你的硬件滤波和基本计数已经生效。但高速时测速算法的量化误差被急剧放大，导致计算出的转速在真实值附近“锯齿震荡”。

## 根因分析：高速下 `dt_us` 量化误差被放大

你的 UTO 目标是每周期约 `N_MIN = 10` 步。高速时：

- **4000 RPM**：周期 = `60s / (4000 / 60 * 4000步)` ≈ **100µs** → `dt_us ≈ 100`
- **8000 RPM**：周期 ≈ **50µs** → `dt_us ≈ 50`
- **12000 RPM**：周期 ≈ **33µs** → `dt_us ≈ 33`

你的时间戳 `us_now = g_tick64 / 60`（60MHz 刻度），`dt_us` 的**分辨率只有 1µs**。

测速公式是：`rpm = dpos × 60e6 / (dt_us × 4000)`

在 12000 RPM 时，`dt_us ≈ 33µs`。如果 UTO 动态周期调整导致 `dpos` 在 9~11 之间跳变（仅有 ±1 步的误差），那么：

| dpos | dt_us | 计算 RPM | 与真实值的偏差 |
|------|-------|----------|---------------|
| 9 | 30 | 4500 | -12.5% |
| 10 | 33 | 4545 | 真实值（基准） |
| 11 | 36 | 4583 | +0.8% |

更严重的是，`dt_us` 本身是整数，如果 `dpos=10` 但 `dt_us` 在 32~34 之间跳变，RPM 会从 4687 跳到 4411，**产生约 5%~6% 的高频抖动**。

**4000 RPM 以下**：`dt_us ≈ 100µs`，1µs 的量化误差只占 1%，抖动不明显。这就是为什么 4000 转以下稳，以上抖。

## 解决方案：改变时间分辨率或增加平滑窗

### 方案 A：放弃 µs 取整，用 64 位刻度差分（推荐）

不要在 ISR 里做 `g_tick64 / 60` 取整，而是**直接用原始刻度差分**计算转速，最后再除以 60：

```c
// 在 TIM5_IRQHandler 中，改用刻度差分：
static uint64_t prev_tick64_raw;
uint32_t dt_tick = (uint32_t)(g_tick64 - prev_tick64_raw);  // 单位：1/60 µs
prev_tick64_raw = g_tick64;

if (dt_tick) {
    int64_t rpm_inst = (int64_t)dpos * 60000000LL * 60LL / (int64_t)dt_tick / 4000;
    // 公式里多乘一个 60，因为 dt_tick = dt_us * 60
}
```

**效果**：时间分辨率从 1µs 提升到 1/60µs（≈16.7ns），12000 RPM 下 `dt_tick ≈ 2000` 刻度，1 个刻度的抖动仅占 0.05%，RPM 抖动被抑制两个数量级。

### 方案 B：多周期滑动窗口平均（更直接）

既然电机惯性大，不需要每个 UTO 周期都更新转速。维护一个**最近 8 个 UTO 周期的 (dpos, dt_tick) 累加和**，每 8 个周期计算一次平均转速：

```c
static uint32_t sum_dpos = 0;
static uint64_t sum_dt_tick = 0;
static uint8_t cycle_cnt = 0;

// 在 ISR 里累加：
sum_dpos += (dpos > 0 ? dpos : -dpos);   // 取绝对值，防反向
sum_dt_tick += dt_tick;
cycle_cnt++;

if (cycle_cnt >= 8) {   // 每 8 个周期算一次平均转速
    int64_t avg_rpm = (int64_t)sum_dpos * 60000000LL * 60LL / sum_dt_tick / 4000;
    g_rpm = (int32_t)avg_rpm;
    sum_dpos = 0; sum_dt_tick = 0; cycle_cnt = 0;
}
```

**效果**：8 周期平均相当于把 12000 RPM 下的有效时间窗从 33µs 拉长到 264µs，机械惯性在此窗口内基本不变，量化噪声被平滑到不足 1%。

### 方案 C：动态调整 EMA 平滑系数（最小改动）

你当前的 EMA α=0.15，在高速下时间常数只有 5~6 个周期（约 150~200µs），相对机械时间常数（几十 ms）太短了。根据转速动态调整 α：

```c
int32_t rpm_abs = g_rpm > 0 ? g_rpm : -g_rpm;
int32_t alpha;  // 千分比，15 = 1.5%
if (rpm_abs < 2000)       alpha = 150;   // 15%，快速跟踪低速变化
else if (rpm_abs < 4000)  alpha = 80;    // 8%
else if (rpm_abs < 6000)  alpha = 40;    // 4%
else                      alpha = 20;    // 2%，高速大幅平滑

g_rpm = (int32_t)(((int64_t)g_rpm * (1000 - alpha) + rpm_inst * alpha) / 1000);
```

## 推荐的组合拳

1. **先用方案 A**（刻度差分代替 µs 取整）——这是“降维打击”，直接消灭量化误差源，代码改动最小。
2. 如果抖动仍明显，再上**方案 B**（8 周期滑动平均）——把高频噪声彻底滤掉。
3. 方案 C（动态 EMA）作为锦上添花。

## 验证建议

修改后，用 `RPM ON` 命令看 8000 RPM 下的实时回显，应该是一条平滑直线而不是锯齿。如果还不行，在 `app_cli.c` 里加一条 `RPM_RAW` 命令，输出未滤波的 `rpm_inst`，对比滤波后看差异——如果 `rpm_inst` 本身已经平滑，那问题在 EMA；如果 `rpm_inst` 就是锯齿，那问题在量化，按方案 A/B 解决。
