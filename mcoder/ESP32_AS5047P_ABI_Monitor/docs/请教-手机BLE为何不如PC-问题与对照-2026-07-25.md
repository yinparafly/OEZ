# 请教：手机 BLE 取数为何不如 PC？问题现象与 PC 行为对照

日期：2026-07-25  
工程：`ESP32_AS5047P_ABI_Monitor`  
对象：ESP32-S3 + AS5047P（ABI）短时转速记录；PC（Python/bleak）与 Android 手机 App 通过 Nordic UART（NUS）连同一块板。

**目的**：把我们踩过的坑、PC 上「能用」的行为、手机上「仍不稳」的现象写清楚，请朋友从 BLE / ESP32 / Android GATT 角度帮忙看一眼设计是否合理、还有没有漏掉的根因。

---

## 1. 系统在做什么（一句话）

```text
MONITOR START 武装
  → 环缓采集
  → |RPM|>门限 + I+1圈（或 1.2s / 环缓较满）触发
  → 回溯 ≤400 点 + 再记约 2s @ 2kHz → INTERNAL RAM
  → ALIVE → SD SAVE（/snap_*.bin 存档）
  → 有 BLE 则发 # BLE PULL READY
  → 主机 DUMP BIN BLE 把点阵拉回（协议：BEGIN / B,seq,hex / END + DUMP ACK）
```

设计意图（见 `docs/蓝牙取数-RAM优先.md`）：

- **SD = 存档**；**BLE 优先读 RAM**（避免 BLE 长传时边读 SD SPI，争用易断链）。
- 记录窗口尽量少往 BLE 灌实时遥测。

当前固件约：`FW=monitor-v35-stream-split`  
手机 APK 约：`1.8.1-bin-dedupe`  
PC：`pc/abi_monitor.py` + `pc/ble_link.py`（bleak）

## 2. 核心矛盾：PC 能用，手机不行（或半通）

| 现象 | PC 蓝牙 | 手机 App |
|------|---------|----------|
| 连接 / 扫到 `OEZ-ABI` | 正常 | 正常 |
| 空闲实时转速 `L,...` | 正常 | 大体正常 |
| 一点「开始监控」/加油触发 | 能记满，不断链 | 易掉线；或记完后拉 RAM 显示空 |
| 记完自动拉数 | `# BLE PULL READY` 后约 **200ms** 拉 | 曾误做成 15s 倒计时；后已对齐 PC |
| `DUMP BIN BLE` | 常 `BIN OK` | 曾一直 `empty RAM`；后来能下到数据但 **实际字节 > 目标、CRC 失败** |
| 停 10s 再连再拉 | 仍能从 RAM/流程拿到数据 | 仍报 RAM 空（有时 SD 回退能下到文件） |

结论直觉：**不是「手机蓝牙坏了」这么简单，而是主机侧行为与 PC 不一致，叠加 Android GATT 特性，把 ESP32 记录窗口冲乱或把回传解包弄坏。**

## 3. PC 参考行为（我们认为「正确主机」）

代码：`pc/ble_link.py`、`pc/abi_monitor.py`。

### 3.1 连接引导

1. `BleakClient` 连接 → MTU 247（失败可忽略）→ `start_notify(TX)`  
2. 等约 **250ms**  
3. 依次发：`TIME <unix_ms>`、`BLE RATE 10`、`ABI?`（间隔约 80ms，Write Without Response）  
4. UI 再补：`TIME`、`REC MS`、再次 `ABI?`  
5. **不设** Android 那种 `CONNECTION_PRIORITY_HIGH`  
6. **不自动重连**（断了要人手点）

### 3.2 收数方式（关键）

- **Notify 为主**；同时对 TX 特征做 **周期性 GATT READ**：
  - 普通约 120ms（Windows）
  - dump / BIN 时约 **40ms**
- READ 有 **去重**：`if val != last_val` 才 ingest（Windows 上 READ 常返回「上一次 Notify 的同一缓冲」，不丢弃会重复）
- 每收到 dump/`B,` 行立刻发 `DUMP ACK\n`（无复杂队列）

> 注意：早期我们误以为「PC 不轮询」。实际上 **PC 在轮询 READ**，这是 Windows 上 BIN 能收齐的重要原因。

### 3.3 监控与拉数

| 动作 | PC |
|------|----|
| 开始监控 | `TIME` → 40ms → `MONITOR START`；**不发 DIAG** |
| 记录中 | 板子 mute 实时流；PC 仍可能 READ（读到很少） |
| 自动拉 | **仅**听到 `# BLE PULL READY` → **200ms** → `SNAP?` → 80ms → `DUMP BIN BLE` |
| 不依赖 | `# CD15` / `# RECORD done` 单独开倒计时（这些只是状态） |
| PING | **从不发** |

### 3.4 取数来源

- 正常：`DUMP BIN BLE` → `src=RAM`  
- SD 仅存档；无 BLE 时 SAVE 后可 `USB DISK ON` 当 U 盘拷 `snap_*.bin`

## 4. 手机曾经做错 / 与 PC 不一致的地方

### 4.1 记录窗口灌包 → 易断链

板子一进 STAGING/RECORD 会 `bleMuteHost`，**停发实时 `L` 帧**。  
手机旧逻辑：遥测一停 → 每 ~350ms `readCharacteristic` + 还发 `PING` → 链路打满 → **一点监控就断**。

PC：不断链（或极少），因为不靠「狂读补遥测」，也不发 PING。

### 4.2 误判「PC 不轮询」→ 矫枉过正

一度改成「记录中完全不 READ」。  
但 PC **在 dump 时必须快 READ**。手机 notify-only 时 ACK/收包更脆。

后来又对齐 PC：空闲/ dump 持续 READ；同时又引出 **重复收包**（见 4.6）。

### 4.3 自动拉时机错误

| | PC | 旧手机 |
|--|----|--------|
| 触发 | `# BLE PULL READY` | `# CD15` / `RECORD done` / `SNAP DONE` 等也会开拉 |
| 延迟 | ~200ms | **15 秒倒计时** |

15s 窗口内容易：用户再点「开始监控」（固件会清 RAM）、断线重连、状态混乱。

### 4.4 连接/武装时多余命令

手机曾在「开始监控」时立刻发 `DIAG`；重连狂发 `REC MS` / `TIME` 等。  
`REC MS` 本身不应当清 RAM，但 **重连命令风暴** + 旧逻辑「TIME 会 abort BIN dump」会表现为「像清空了」。

固件侧已收紧：`MONITOR START` → `snapArmBegin()` **才会清空上一拍 RAM**；空环缓触发禁止抹已有数据。

### 4.5 高优先级 + 自动重连

手机：`CONNECTION_PRIORITY_HIGH` + 掉线自动重连。  
PC：都没有。  
重连风暴容易撞在 STAGING/RECORD/SAVE 窗口。

### 4.6 Notify + READ 双通道重复 → 字节超标、CRC 失败（最近一次）

现象：

- 界面仍提示 **RAM 空**（板内 snap 计数为 0，走了 **SD 回退** 或空 RAM 提示）  
- 但 **数据确实在下**  
- **已收字节 > BEGIN 里的 `bytes=`**  
- **CRC 失败**

根因（高度确信）：

Android 上 GATT **Notify 已交付一包**后，`readCharacteristic(TX)` 常读到 **同一特征值内容**。  
手机旧代码两路都 `ingest` → 每个 `B,<seq>,<hex>` 写进缓冲 **两次** → 长度翻倍 → CRC 必挂。

PC 用 `last_val` 去重，所以没事。

已在 APK `1.8.1` 修：

1. 相同 payload 直接丢弃（对齐 PC `last_val`）  
2. 按 `B,seq` 去重  
3. 超过 `bytes=` 时截断再解析  

（请朋友确认：Android 上「Notify 后再 READ 同一 CCCD 特征」是否普遍如此；有无更干净的「dump 时只走 Notify、丢包再 READ」策略。）

### 4.7 流分离（已按产品意图落地）

用户建议、我们认为合理：

```text
未监控：BLE 发实时转速 L
一开始 MONITOR：BLE 停发实时转速；只发短事件
  （# QUIET / # CONFIRM / # RECORD done / # CD15 / # BLE PULL READY）
记完/停止：再恢复实时转速
```

固件 v35 + 手机武装期间停轮询，就是这个「完全分离」。  
USB 串口仍始终有完整 `L,`，方便 PC 调试。

## 5. 数据路径对照图

```text
                    ┌──────────── ESP32 ────────────┐
                    │  2kHz → RAM snap               │
                    │       → SD /snap_*.bin         │
                    └─────────────┬──────────────────┘
                                  │
           ┌──────────────────────┼──────────────────────┐
           ▼                      ▼                      ▼
     PC bleak              手机 GATT                 USB MSC/拔卡
  notify+READ去重         notify+READ（易重复）      直接读文件
  PULL READY+200ms        曾 15s / 多触发源          snap_*.bin
  DUMP BIN BLE            DUMP BIN BLE              （无 BLE 争用）
  src=RAM 为主            RAM 空 → 已加 SD 回退
```

协议（两端相同）：

```text
# BIN BLE BEGIN src=RAM|SD n=… hz=… bytes=… crc=0x…
B,0,<hex>
B,1,<hex>
…
# BIN BLE END … ok=1 crc=0x…
主机每包：DUMP ACK
```

## 6. 当前状态（写文档时）

**已对齐 / 已修：**

- 流分离：武装后停 BLE 实时转速  
- 拉数时机：对齐 PC 的 `BLE PULL READY` + 200ms  
- 去掉监控时 DIAG / PING / 自动重连 / HIGH priority（手机侧）  
- RAM 空时固件可 **先读完 SD 最新 snap 再 BLE 传**（避免边传边读卡）  
- 手机 BIN **去重 + 截断**，修「数量偏大 + CRC 失败」

**仍可疑 / 想请教：**

1. **为何手机会话下 RAM 经常为 0？**  
   - 触发从未成功？（环缓有、正式段无）  
   - 采样在手机连接时被 BLE 栈拖死？  
   - 用户再次 `MONITOR START` 清掉了上一拍？  
   - SD 有文件说明至少某次 SAVE 成功过——是 PC 那次还是手机那次？

2. **Android 上 dump 最佳收包策略？**  
   - 仅 Notify + 超时才 READ？  
   - 还是像 PC 一样持续 READ + 强去重？（我们现在偏后者）

3. **NimBLE + 2kHz 采样 + GATT READ** 是否仍建议在 RECORD 窗口完全禁止主机 READ？

4. SD 回退是否应成为手机主路径，RAM 仅作「刚记完立刻拉」的快路径？

## 9. 附录：命令与事件速查

**主机 → 板**

- `TIME <ms>` / `BLE RATE 10` / `ABI?` / `REC MS <ms>`  
- `MONITOR START` / `MONITOR STOP`  
- `DUMP BIN BLE`（RAM；空则固件可回退 SD）  
- `DUMP BIN BLE SD`（强制最新 `/snap_*.bin`）  
- `DUMP ACK`（每包）  
- `SNAP?` / `DIAG`

**板 → 主机（BLE 事件，监控中）**

- `# MONITOR armed — BLE live RPM OFF…`  
- `# QUIET`（进入 STAGING）  
- `# CONFIRM seg=…`  
- `# RECORD done …` / `# CD15 …`  
- `# BLE PULL READY src=RAM`  
- `# BIN BLE BEGIN/END …`

**板 → 主机（仅未武装）**

- 短帧 `L,rpm,dir,armed,phase,remain,snap_n`
