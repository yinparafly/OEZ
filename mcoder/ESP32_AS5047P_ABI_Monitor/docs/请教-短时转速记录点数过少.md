# 请教：ESP32 短时转速记录「应有几千点，实际只有几十点」

> 目的：把我们的硬件、做法、异常现象和疑问写清楚，方便朋友帮忙判断——  
> **是计数/采样本身有问题，还是「记完后 USB 回传」链路有问题，还是软件状态机搞复杂了。**

---

## 1. 我们要做什么

场景：**电机已经转起来**（或弹射瞬间加速），需要把大约 **1 秒** 的 ABI 转速曲线采下来，落到 PC，再分析峰值转速、时长、大致转过几圈。

期望数量级：

| 采样率 | 记录时长 | 理论点数 |
|--------|----------|----------|
| **2 kHz** | **1 s** | **≈ 2000 点** |
| （若含触发前追点 ~0.4 s） | | 约 2400～2800 点 |

实际落盘却经常只有 **几～几十个点**（例如 9 点 / 59 点，时长只有几～几十毫秒）。  
**转速为 0 也是合法采样**；我们说的「空/几乎没有」是指 **点数极少或 0 个点**，不是「RPM 显示为 0」。

## 2. 硬件与工程

| 项 | 说明 |
|----|------|
| MCU | ESP32-S3（带 PSRAM，FQBN 开了 `PSRAM=opi`） |
| 传感器 | AS5047P，**ABI 正交 + I 索引** |
| 接线 | A→GPIO15，B→GPIO16，I→GPIO17 |
| 计数 | ESP-IDF **PCNT** 累计 A/B；`esp_timer` 周期采样算转速 |
| 通信 | USB CDC 串口 **921600**；另有 BLE（本问题主要卡在 USB） |
| 固件目录 | `ESP32_AS5047P_ABI_Monitor/firmware/ESP32AbiMonitor/` |
| PC | `pc/abi_monitor.py`（Tk），落盘 `pc/logs/` |
| 参考工程 | 朋友侧有可用的短突发记录思路（约 0.5 s @400 Hz，`READ` → `DATA_START|N` … `DATA_END`） |

单点结构（板内 RAM，约 12 字节/点）：

```text
t_ms, rpm_x10 (int16), seg, index_n
```

监控日志缓冲：`log_cap≈12000`（**INTERNAL RAM**，故意不用 PSRAM 给 2 kHz 定时器写，以免踩坑）。

---

## 3. 当前「应该怎么走」的流程

### 3.1 最初产品设想（弹射 / 门限路径）

1. PC 发 `MONITOR START`（可先静止武装）  
2. `|RPM| > 20` → 进临时池 STAGING  
3. 短窗内净转角达标（约 1/8 圈）→ **CONFIRM**，把临时池最近约 `BACKTRACK_N=800` 点（~0.4 s@2kHz）写入主记录  
4. 再 **RECORD 1000 ms**（再写约 2000 点）  
5. `# RECORD done … log_n≈2000+` → 回传到 PC → 存 CSV  

### 3.2 为排查「点数过少」后来简化的直采路径

用户要求：**先开电机，点一下就采满 1 s，不要任何门限/确认判断。**

**当前推荐（朋友方案，v17）**：

- 命令：`REC` / `REC NOW` → 2 kHz **整数** ISR 写入内部 RAM（~3000×12B）  
- 满 1 s 只打一行：`# SNAP DONE n≈2000`（不自动灌文本）  
- PC 发 `DUMP BIN` → 停定时器 → `magic(4)+n(2)+hz(2)+n×12+CRC32(4)` → 再开定时器  
- PC 校验 CRC 后落盘 CSV  

（固件：`FW=monitor-v17-snapbin`）

旧文本 `LOG DUMP` / 门限 MONITOR 仍保留作对照，但短时 1 s 应以 **DUMP BIN** 为准。

## 4. 我们实际看到的现象（关键证据）

### 4.1 有时板上「明明记够了」

串口曾多次出现类似：

```text
# CONFIRM … → RECORD 1000ms
# RECORD done seg=1 log_n=2046
# RECORD done seg=1 log_n=2057
```

说明：**在板内 RAM 里，曾经成功写出约 2000 点**。  
因此我们倾向认为：**PCNT + 2 kHz 写缓冲，至少在部分时刻是通的**，不像「底层永远数不到」。

### 4.2 但 PC 落盘经常只有残片

已保存的例子（`pc/logs/`）：

| 目录 | 点数 | 时间跨度 | 说明 |
|------|------|----------|------|
| `20260724_190046` | **59** | ~29 ms | t_ms 连续，约 0.5 ms 间隔（像 2 kHz 残段） |
| `20260724_190928` | **9** | ~4 ms | 同样是残段；PC 日志有 `dump stall → force finish n=9` |

也就是说：**要么板内其实只有这么短一段，要么板内很多、USB 回传只收到开头一点。**

### 4.3 记完后板子「整段开机横幅又来一遍」

典型顺序：

```text
# RECORD done seg=1 log_n=2057 …
# ESP32 AS5047P ABI Monitor FW=…   ← 像复位/重启
# logAlloc …
# ready.
>> LOG DUMP USB
# LOG empty
```

若真是复位，**RAM 日志会被清掉**，之后 DUMP 空是必然的。  
曾出现过 `Guru Meditation` / `Coprocessor exception`（怀疑与 **定时器回调里用 float**，同时主循环 `printf`/DUMP 也碰 FPU 有关）。

### 4.4 实时转速往往是正常的

电机高速转时，PC 上实时 `L,…` 转速数字能跟上。  
这更支持：**计数链路大致在工作**；烂的是「武装→记满→完整拉回 PC」这条产品路径。

### 4.5 我们自己也把链路弄复杂了

为了躲复位、躲 CDC 堵死，来回改过很多版，例如：

- 记完立刻 `freeze` 停采样 → 曾导致「电机在转、板子已不采」  
- 板子 AUTO DUMP 狂推几千行 USB 文本 → 易堵/断/只收到几十行  
- 改成只发 `READY`、等 PC `LOG DUMP` → 有时 PC 没拉到就「没数据」  
- 再加 1.2 s 板子 FALLBACK 自推、stall 超时强制收尾 → 又容易把残片当成完整结果  

所以请教时也希望朋友帮忙看：**是不是软件策略过度复杂，反而掩盖了真正的根因。**

## 5. 回传方式（当前大致实现）

DUMP 是 **文本行**，不是二进制，例如：

```text
D,<t_ms>,<rpm>,<dir>,<seg>,<index_n>
…
D END <n> segs=…
```

USB 上为减轻 CDC 压力做过 pacing（例如每 8 行 `flush` + `delay(2)`）。  
按 2000 行估算，完整 DUMP 可能要数秒；若中途复位或 PC 提前 `force finish`，就会只剩几十点。

对比参考工程思路：短突发 + 主机 `READ` + `DATA_START|N` … `DATA_END`，包更规整，我们这边一直在「文本洪水 vs 可靠性」之间摇摆。

## 6. 我们的判断（不完全确定）

| 判断 | 依据 | 不确定点 |
|------|------|----------|
| **底层 ABI/PCNT 大概率不是「完全坏」** | 实时 RPM 正常；多次 `log_n≈2000` | 高速时是否偶发丢计数未系统验证 |
| **「几千点变几十点」更像回传/复位/提前收尾** | RECORD done 大 `log_n` 后出现开机横幅或 stall n=9 | 需要在 RECORD done 后立刻 `LOG?` 看板内 `log_n` 是否还在 |
| **门限/确认状态机曾让「转了却不记」** | 未武装、freeze 卡住、噪声丢弃 | 直采 `REC NOW` 就是为去掉这层 |
| **0 RPM ≠ 空数据** | 记录窗口内停转仍应有采样点 | 分析文案曾误导 |

## 7. 想请教朋友的问题（请按优先级指点）

1. **如何一锤定音区分「板内没写够」vs「写够了但 USB 没拉全」？**  
   例如：RECORD 结束立刻只打印 `log_n` / 校验和，不 DUMP；或 DUMP 前先发 `expect_D=`，PC 必须收到 `D END` 且 `n≈expect` 才存盘。

2. **ESP32-S3 USB CDC @921600 连续打 ~2000 行文本，稳妥做法是什么？**  
   二进制块？更小波特？主机 ACK 分块（对齐你们可用的短突发协议）？DMA？加大 TX 缓冲是否有用？

3. **`esp_timer` 2 kHz 回调里用 float 算 RPM，主循环再 Serial 导出——是否必须彻底禁止「采样与 DUMP 并发」？**  
   停 timer 再 DUMP 是否足够？是否还要关中断/迁到另一核？

4. **若目标只是「电机已转 → 点一下 → 稳拿 1 s@2kHz≈2000 点」**，你们会如何做最小架构？  
   （我们准备把门限/确认全部旁路，只留 `REC NOW` + 可靠 DUMP。）

5. **PSRAM 能否给 2 kHz ISR 写日志？** 我们目前强制 INTERNAL，是否过度保守？

6. **若朋友方便**：有没有推荐的「短记录 + 可靠拉回」开源/现成模式（不必是 ABI，加速度计短突发也行），我们可以对照改。

## 8. 复现步骤（给朋友或自己）

1. 烧录当前监控固件，确认开机行含 `FW=monitor-v17-snapbin` / `DUMP BIN`。  
2. PC：`python abi_monitor.py --usb`，连接 COM（二进制路径仅 USB）。  
3. **先让电机转起来**，再点「① 采1秒」或发 `REC NOW`。  
4. 期望串口顺序：  
   - `# REC NOW … SNAP`  
   - `# SNAP DONE n≈2000`  
   - `# BIN BEGIN …` → 二进制块 → `# BIN END … crc=…`  
   - PC 日志 `# BIN OK n=… CRC ok`，CSV 约 2000 行  
5. 若 `SNAP DONE n≈2000` 但 BIN 失败：把十六进制头 16 字节与 `# BIN END` 行贴出。  
6. 旧文本 `LOG DUMP` 仅作对照，短时记录请以 **DUMP BIN** 为准。

## 9. 一句话总结

朋友诊断成立：**根因在 USB 文本回传/复位，不在 PCNT。**  
已按「记录与回传分离 + 二进制块 + CRC」落地为 `monitor-v17-snapbin`。  
**验证标准：SNAP DONE n≈2000 且 BIN OK / CSV ≈2000 行。**
