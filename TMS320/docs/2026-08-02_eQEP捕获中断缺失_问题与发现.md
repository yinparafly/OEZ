# 问题与发现：F28P55x eQEP 捕获单元没有中断（2026-08-02）

> 目的：记录在"天机星 TMS320F28P550 事件驱动测速记录器"开发中发现的一组硬件/驱动问题，供向 TI 工程师、C2000 老手请教。
> 结论来源：**TI 官方头文件（C2000Ware 5.04 driverlib）+ TI 官方示例静态分析**，尚未上板实测（板子还没接）。
> 相关工程：`D:\oezcon\TMS320\AbiMonitor_TJX\`（模板自 `device\driverlib\` 自带 TI 官方源码）。
> 版本：2026-08-02 v3（主频修正 150MHz + 三位朋友答复确认，见"三朋友答复"节）。

## 背景

我们想用 eQEP 做**事件驱动（非均匀采样）测速记录**：ABI 编码器（1000PPR，4X=4000 计数/圈），
希望 **每个 ABI 边沿触发一次中断**，ISR 里读时间戳 + 计数写入 16B 事件点 (t_us, counts, index_n)，
设计上限 20000rpm（4X 时 1.33M 边沿/s，即 0.75µs/边沿），ISR 预算 0.6µs（90 周期 @150MHz）。

**主频：F28P55x = 150MHz**（C28x 内核；device.h L299 公式 20MHz×30/(2×1×2)=150MHz 与数据手册一致，
2026-08-02 由朋友 G 指出并核实）。

原计划假设 eQEP 捕获单元（QCAP）有"捕获周期就绪"中断（`EQEP_INT_CAPTURE_PERIOD`），
经核对头文件，**该中断不存在**，核心架构需要改。

---

## 问题一（核心）：eQEP 捕获单元根本没有中断

**证据 1 — QCAPCTL 寄存器无中断使能位**
`AbiMonitor_TJX\device\driverlib\inc\hw_eqep.h` L123-130：
```
QCAPCTL 只有三个字段：
  UPPS  (Unit position event prescaler,   bits 0-3)
  CCPS  (Capture timer clock prescaler,   bits 4-6)
  CEN   (Enable capture,                  bit 15)
```
捕获单元没有自己的中断使能位。

**证据 2 — QFLG 中断标志只有 13 个，没有捕获标志**
`hw_eqep.h` L164-179（完整列表）：
```
QFLG_INT    全局中断
QFLG_PCE    位置计数错误
QFLG_PHE    相位错误
QFLG_QDC    方向改变
QFLG_WTO    看门狗超时
QFLG_PCU    位置计数下溢
QFLG_PCO    位置计数上溢
QFLG_PCR    位置比较就绪
QFLG_PCM    位置比较匹配
QFLG_SEL    Strobe 事件锁存
QFLG_IEL    Index 事件锁存
QFLG_UTO    单位时间超时
QFLG_QMAE   QMA 错误
```
**没有**"捕获周期就绪 / 捕获事件"标志。即 QCPRD 每边沿更新一次，但**没有任何中断会通知你**。

**证据 3 — TI 官方示例也是绕开捕获中断的**
`D:\ti\c2000ware\C2000Ware_5_04_00_00\driverlib\f28p55x\examples\eqep\eqep_ex4_freq_cal_interrupt.c`
标题即 "Frequency Measurement Using eQEP **via unit timeout interrupt**"——
用 UTO 中断 + 轮询 QPOSCNT 测频，捕获单元只做硬件锁存、不产生中断。

**证据 4 — driverlib API 印证**
`eqep.h`：
- `EQEP_enableCapture(uint32_t base)` —— 只有一个参数，没有"中断模式"参数（L979-991）
- `EQEP_setCaptureConfig(base, capPrescale, evntPrescale)` —— 只有两个分频参数，无边沿极性/中断参数（L950-966）

## 问题二：原计划假设的枚举名在头文件里不存在

原计划写了这些名字，**全部不存在**，编译会直接报错：
| 原假设名 | 实际 |
|---|---|
| `EQEP_INT_CAPTURE_PERIOD` | 不存在（QFLG 无此标志） |
| `EQEP_INT_INDEX_EVENT` | 不存在，正确名是 **`EQEP_INT_INDEX_EVNT_LATCH`**（eqep.h L144） |
| `EQEP_CAPTURE_BOTH_RISING_FALLING` / `EQEP_CAPTURE_POS_RISING` | 不存在（setCaptureConfig 只有两个分频参数） |
| `EQEP_enableCapture(..., EQEP_CAPTURE_PERIOD_READY)` | 不存在（只有单参数版本） |
| `EQEP_intEnable(...)` | 正确名是 `EQEP_enableInterrupt(base, intFlags)`（eqep.h L648） |
| `EQEP_CONFIG_4X_RESOLUTION` | 不存在！ |

**关于"4X"的重要澄清（v2 修正）**：
- 分辨率枚举只有 `EQEP_CONFIG_1X_RESOLUTION`(0x0800) 和 `EQEP_CONFIG_2X_RESOLUTION`(0x0000)（eqep.h L90-91），
  它们映射到 **QDECCTL.XCR（External Clock Rate）** 位（hw_eqep.h L93）。
- **XCR 只对"方向-计数（CLOCK_DIR）模式"生效**（XCR=0 双沿计数、XCR=1 仅上升沿）。
- 在**正交（Quadrature, QSRC=00）模式下，计数天然就是 4X**（A、B 各两个边沿都计），没有 1X/2X/4X 可选。
- 结论：canonical 4000 计数/圈**可以实现**（正交模式默认行为），但原计划的
  **"运行时切换 1X/4X 分辨率降 ISR 速率"在正交模式下做不到**——只能用软件等效方案
  （PCM 步长切换：QPOSCMP=QPOSCNT±N，N 从 1 调大，见方案 A 第 10 条）。

## 问题三：QCPRD/QCTMR 是 16 位寄存器，低速直接溢出

`EQEP_getCapturePeriod` / `EQEP_getCaptureTimer` 返回 **uint16_t**（eqep.h L1030-1067）。
CAPCLK=SYSCLK=150MHz 时，16 位最大值 65535 tick ≈ **436.9µs**：

- 边沿间隔 > 436.9µs（即 < 2289 边沿/s ≈ **34.3rpm** @4000 计数/圈）→ QCPRD 溢出，周期测速失效。
- 想测更低速，只能把 CAPCLK 分频（CCPS），但会损失高速时的 µs 分辨率，且分频值要按速度切换。

（v2 曾按 200MHz 估算 327µs/46rpm，主频修正后一并更新。）

（原计划写的是 `uint32_t period = EQEP_getCapturePeriod(...)`，类型对了但没意识到 16 位上限。）

---

## 问题四：QCTMR 每捕获事件清零，不能当绝对时间戳

原计划设想用 QCTMR 扩展成 64 位单调 µs 时钟（回绕计数），
但 QCTMR 在**每个捕获边沿会清零**（锁存进 QCPRD 后复位），不是自由运行计数器，
回绕检测逻辑失效。绝对时间戳应改用 **CPUTIMER0 自由运行 + 1kHz ISR 维护回绕计数**。

---

## 问题五：EPG 模块也没有边沿周期测量中断

F28P55x 有 EPG 模块，但其中断只有 `EPG_INT_SIGGEN0_DONE` / `EPG_INT_SIGGEN0_FILL`
（epg.h L309-311，信号发生器输出侧），**没有输入边沿周期测量中断**，不能用来替代捕获中断。

---

## 我选的替代方案（方案 A：位置比较 PCM 逐计数中断）

既然硬件没有"捕获中断"，用**位置比较匹配**模拟逐计数中断：

1. `EQEP_enableCompare()`（QPOSCTL.PCE=1）
2. QPOSCTL 置 **PCSHDW=1 + PCLOAD=1**（影子使能、匹配时自动装载影子值）
3. ISR 每次匹配后写 `QPOSCMP = QPOSCNT ± 1`（方向用 `EQEP_getDirection()` 返回 ±1）→ 每个计数变化触发一次 PCM 中断
4. 方向反转时 QPOSCNT 会背离 QPOSCMP → 用 **QDC（方向改变）中断**重新武装
5. Index 用 **IEL**（`EQEP_INT_INDEX_EVNT_LATCH`）
6. 三个源都在**同一条 INT_EQEP1**，一个 ISR 里读 QFLG 分发
7. 时间戳：CPUTIMER0 自由运行 @SYSCLK + 1kHz ISR 维护 64 位 µs 时钟
8. 周期测速：ISR 内用 µs 时钟差分（上一事件时间差值），**不依赖 QCAP**
9. 捕获单元干脆不启用（16 位溢出 + 无中断，没收益）
10. **分档降 ISR 速率**：正交模式无法切硬件分辨率（见问题二），改用软件等效——
    `QPOSCMP = QPOSCNT ± N`（N=1 逐计数；高速时 N=4/8，ISR 速率同比例下降），
    QPOSCNT 差值仍精确，canonical 计数不丢。
11. 极端速率下 ISR 追不上时，靠 QPOSCNT 差值追赶（计数精确、中间边沿时间丢失）→ 优雅降级

**备选方案 B（留作将来对比）：UNIT_TIME_OUT 周期采样**
TI 官方 ex4 模式，UTO 中断 + 轮询 QPOSCNT/QCPRD，1kHz（或更高）采样。
实现最简单、最稳，但每个 tick 只记 1 点（6500rpm 时每 ms 就有 433 个计数），逐边沿事件时间全丢。

## 三朋友答复（2026-08-02，全部确认核心结论）

三位朋友（G / k / dp）对本文档的答复存档：
`TMS320/docs/superpowers/specs/G答复.txt`、`k答复.txt`、`dp 答复1.txt`。

**一致确认**：
- QCAP 无中断、无隐藏路径（中断路径完全由 QFLG/QEINT 控制，QCAP 不在其中；eQEP 共 11 个中断源 PCE/PHE/QDC/WTO/PCU/PCO/PCR/PCM/SEL/IEL/UTO）。
- 正交模式恒 4X；XCR 只对 CLOCK_DIR 模式生效（dp 逐条确认）。
- QCPRD 16 位、QCTMR 清零；官方做法就是 UTO 轮询，不依赖 QCPRD（ex5 同款）。
- 方案 A 可行：k 评 ★★★★ 首选；dp 称"极具创造性的变通"，TI E2E 有人讨论过类似思路；ISR 追不上时"只丢中间边沿时间、计数不丢"的理解正确（优雅降级）。

**关键修正（G）**：**F28P55x 主频是 150MHz，不是 200MHz**——已核实（device.h L299 公式 + 用户确认数据手册）。
影响：ISR 预算 90 周期/0.6µs；QCPRD 溢出 436.9µs≈34.3rpm；921600 波特率 @LSPCLK=37.5MHz 实际 937500、误差 +1.72% <±2% **可直接用**（原 -3.1% 作废）。

**已吸收的加固建议（k）**：
1. ISR 开头先读 QPOSCNT + 时间戳，再分发 QFLG（缩小窗口）。
2. 加**漏事件计数器**（本次 delta > step 时累加），联调时观察优雅降级。
3. 中高速自动加大 N（按最近速度估计），低速 N=1。
4. QPOSCMP 写完后再清中断标志（影子时序）。
5. 回绕（QPOSMAX→0）匹配行为上板实测。

**已吸收的行动建议（G）**：Task 6 加强制检查点——先做极简 PCM 验证（100kHz 模拟脉冲测 CPU 占用），>0.6µs 立即降档，不拖到联调。

**其他路线评估（dp/G）**：GPIO XINT（无 4X 解码、噪声敏感 ★★）；CLB+XBAR+DMA（开发成本高 ★，后期优化）；eCAP（有边沿中断但 1-2 路无法同时处理 A+B 正交，不适合）。**均不改变方案 A 选型**。

## 想请教的问题清单（2026-08-02 已获答复，要点内联标注）

1. **QCAP 真的完全没有中断吗？** 是否有什么隐藏路径（TRM 里哪个章节？）让捕获事件触发 CPU/CLA/DMA？
   → 确认无。唯一隐藏路径是 **DMA 触发**（dp：需查具体触发源列表），但 DMA 只能搬运数据、无法记录时间戳，对本项目无实质帮助。
2. **方案 A（PCM 逐计数）有没有坑？**
   - QPOSCMP 影子装载时序：PCLOAD=1 在匹配时装载，ISR 里写影子值会不会有竞争？
     → dp：无竞争，PCLOAD=1 时硬件在匹配周期自动装载影子值，ISR 只需在下次匹配前更新影子寄存器。
   - QPOSCNT 到 0xFFFFFFFF（MAX_POS 模式）回绕到 0 的瞬间匹配行为？→ 需上板实测（三人一致）。
   - ISR 追不上时（delta>1）只丢"中间边沿时间"、计数不丢，这个理解对不对？→ 正确（三人一致）。
   - 有没有人这么干过（Ti E2E 帖子？）？→ dp：E2E 有人讨论过类似想法，非主流但可行。
3. **QCPRD 16 位溢出**：TI 官方的低速测速做法是什么？CCPS 动态分频？
   → 官方做法是 UTO 中断轮询 QPOSCNT 差分（ex4/ex5），完全绕开 QCPRD。
4. **还有没有别的 C2000 事件驱动方案**（GPIO XINT、CLB→输出 XBAR、DMA 之类）？
   → 见"三朋友答复"节其他路线评估。
5. **QDECCTL.XCR 语义确认**：1X/2X 分辨率是否真的只对 CLOCK_DIR 模式生效？
   正交模式下是否真的固定 4X、无法动态降分辨率？→ 确认：XCR 只在 QSRC=01（CLOCK_DIR）生效，正交模式恒 4X（dp 明确确认）。
