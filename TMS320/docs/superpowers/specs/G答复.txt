### 一、 对你们发现的“核心问题”之确认与赞赏

首先必须高度肯定你们的这轮复盘（v2）。你们通过查阅 `C2000Ware 5.04 driverlib` 头文件、寄存器定义（`hw_eqep.h`）以及 TI 官方例程（`eqep_ex4_freq_cal_interrupt.c`），得出的结论完全正确：

1. **确实没有 QCAP 捕获中断**：QCAP 寄存器只有时钟分频和使能位，QFLG 中断标志中也确实不包含任何捕获就绪标志。QCPRD 虽能硬件锁存，但它只能靠主循环/定时器轮询，无法实现“每个边沿触发 ISR”。


2. **正交模式（QSRC=00）下硬件天然是 4X**，无法在正交模式下通过寄存器位动态切换 1X/4X（XCR 只对 CLOCK_DIR 模式生效）。


3. **16 位 QCPRD 溢出问题**（满载 65535 约 327µs，即约 46rpm 就会溢出）以及 **QCTMR 会在捕获后清零**，导致原设想的“用 QCTMR 扩展 64 位时间戳”行不通。



这说明你们的工程团队在没有上板前就通过“静态代码分析”排除了一个重大的架构级坑，避免了盲目上板调试带来的巨大时间浪费。

### 二、 针对你们提出的“替代方案 A（位置比较 PCM 逐计数中断）”的深度剖析

你们提出的**方案 A（利用位置比较器匹配产生中断：`QPOSCMP = QPOSCNT ± 1`）** 是一个非常聪明的纯软件闭环补救思路。针对你们的疑问清单，逐一进行技术剖析：

#### 1. 方案 A 的可行性与潜在“坑”

* **QPOSCMP 影子装载与竞争冒险**：
* **分析**：当配置 `PCSHDW=1`（影子模式）且 `PCLOAD=1`（当 `QPOSCNT == QPOSCMP` 时加载）时，硬件会在匹配发生的那个时钟周期自动把影子寄存器的值加载到活动寄存器中。
* **风险**：如果在 ISR 响应期间（通常需要几十个 CPU 周期），电机转速极高，QPOSCNT 已经连续跳变了好几个数，此时在 ISR 里盲目写 `QPOSCMP = QPOSCNT ± 1`，可能会导致下一次匹配点错乱或漏掉。必须在 ISR 里根据当前的实际 `QPOSCNT` 相对动态更新（例如写成 `QPOSCNT + 1` 或 `QPOSCNT - 1`），而不是简单的 `+= 1`。


* **QPOSCNT 边界回绕（0xFFFFFFFF ↔ 0）**：
* **分析**：eQEP 的位置计数器是 32 位的（在 `MAX_POS` 模式下）。当计数器从 `0xFFFFFFFF` 跨越到 `0`（或反向）时，如果你的 `QPOSCMP` 刚好设在临界点附近，硬件会自动处理回绕，但你的软件逻辑必须妥善处理 `int64_t counts` 的单调累加，不能因为硬件回绕导致 `counts` 出现阶跃。


* **ISR 追不上时的表现（Delta > 1）**：
* **分析**：你们的判断基本正确——**“只丢中间边沿时间，不丢总计数”**。但是，对于你们的项目目标——**“非均匀采样测速记录器，还原扑翼/弹射速度轨迹”** 来说，如果高速段（如 12000 RPM 对应的 400kHz 事件率）发生 ISR 追不上（Delta > 1），意味着那几个边沿的精确 `t_us` 时间戳丢失了。这会直接破坏你们在 §3.1 中强调的“低速不量化、高速不丢边沿/真实还原轨迹”的设计初衷。





#### 2. 高速下的致命瓶颈（性能账本）

* TMS320F28P550 主频是 **150MHz**（注意：你们文档里部分地方写了 200MHz，根据官方数据手册，F28P55x 的 CPU 主频是 **150MHz**，单个周期约 `6.67ns`）。


* 在扑翼机高速区（12000 RPM，4X 下事件率达 **400kHz**，即平均每 **2.5µs** 就有一个边沿）：


* 400kHz 对应的事件间隔只有 **375 个 CPU 周期**（@150MHz）。
* 如果采用方案 A（每个边沿都进一次 PCM 中断），意味着 CPU 必须在 375 个周期内完成：进入 ISR、读时间戳、读 QPOSCNT、更新 QPOSCMP、写环形缓冲区、退出 ISR。
* 这对 C2000 纯软件逐边沿中断的开销挑战极大，极易引起 CPU 负载 100% 甚至卡死。

### 三、 官方视角：有没有更好的替代路线？

既然纯软件用 PCM 模拟逐边沿中断在 400kHz 高事件率下存在性能瓶颈，建议评估以下两种更符合 C2000 硬件特性的架构路线：

#### 替代路线 1：回归官方例程的“高频定时器/UTO 轮询流”（推荐用于高速段）

* **思路**：放弃“每个边沿必须进一次 ISR”的执念，改用 **CPU 定时器（如 20kHz ~ 50kHz）** 或 **eQEP 自身的单位时间超时中断（UTO，Unit Time Out）**。
* **原理**：在 UTO 或高频定时器中断里，直接读取当前的 `QPOSCNT` 和硬件自动锁存的 `QCPRD`。
* **优势**：
* 完全避开了高频边沿进 ISR 的 CPU 灾难。
* 测速精度极高（利用了 QCPRD 硬件测周期能力）。


* **对你们项目的影响**：事件点变成了一定时间窗口内的平均或精准瞬时采样，虽然不是绝对的“每个物理边沿一个点”，但在 50kHz 采样率下，对于 12000 RPM 的扑翼轨迹还原已经足够平滑，且固件极其稳健，绝对不会发生 ISR 跑满。

#### 替代路线 2：利用 F28P55x 的杀手锏 —— CLB（可配置逻辑块） + XBAR + DMA

* **提示**：F28P55x 系列的一个巨大优势是内部集成了 **2 个 CLB（可配置逻辑块）**，这相当于一个片上的小 FPGA。


* **思路**：
* 让 ABI 信号同时走硬件引脚输入到 CLB。
* 用 CLB 内部搭建自定义的边沿检测与时间戳锁存逻辑，或者利用 **eCAP 模块**（F28P55x 有 2 个 eCAP 模块）配合 Input XBAR 来捕获 A 相或 B 相的边沿。


* 当边沿到来时，通过 **DMA** 自动把时间戳和计数搬运到 RAM 的环形缓冲区中，**全程不需要 CPU 进 ISR**！
